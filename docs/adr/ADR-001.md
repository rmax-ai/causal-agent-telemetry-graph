# ADR-001 — Immutable Ledger + Graph Projection

- **Status:** Accepted (SPEC.md §7)
- **Source:** SPEC.md §7 (Architectural rule), §11 (Storage Design), §4 (MVP Must/Should), §9 (Canonical Event Schema / Idempotency), §25 (Acceptance Criteria); ARCHITECTURE.md §2, §8

## Context

CATG ingests heterogeneous, potentially out-of-order agent telemetry from ADR, OpenTelemetry, and MCP sources (SPEC.md §1, §3). The system needs one durable, authoritative record that:

- can absorb out-of-order and asynchronous enrichment without rewriting history (SPEC.md §3 — "Out-of-order heterogeneous sources: Append-only canonical events and asynchronous enrichment");
- stores immutable evidence *before* any derived graph state exists (SPEC.md §4 — "Store immutable evidence before derived graph state");
- supports idempotent re-import of the same source records (SPEC.md §9 — `dedupe_key` unique index);
- can be re-projected and schema-migrated by rebuilding (SPEC.md §4 — "Allow re-projection from canonical events", "Support graph schema migrations by rebuilding the projection").

A solo engineer, part-time, 6–8 week MVP and a one-command local setup rule out external services, so storage is embedded: SQLite for the ledger, Kuzu for the graph (SPEC.md §3, §7, §11).

## Decision

**The SQLite append-only event ledger is authoritative; Kuzu is a rebuildable materialized projection** (SPEC.md §7, "Architectural rule").

- Canonical events are stored in SQLite tables `events`, `projection_checkpoints`, `quarantine_records`; append-only is enforced by triggers rejecting UPDATE/DELETE outside test builds (SPEC.md §11).
- Idempotency: stable `eventId` from the source when available; otherwise `dedupe_key = SHA256(tenant_id || source_kind || source_record_id || normalized_event_type || normalized_occurred_at || canonical_payload_hash)` with a unique index on `(tenant_id, dedupe_key)` (SPEC.md §9).
- The Kuzu graph (physical tables Principal, Agent, Execution, Communication, Tooling, Asset, Governance, Outcome, EvidenceArtifact) is always rebuildable from the ledger (SPEC.md §11).
- Kuzu driver limitations are encapsulated; SQLite remains the durable truth (SPEC.md §24 risk "Kuzu Node binding limitations" — mitigate by "encapsulate driver; retain SQLite").

## Consequences

### Positive

- Source of truth is simple, single, and append-only — auditability and rebuildability are guaranteed by construction (SPEC.md §7, §11).
- Duplicate imports are rejected/deduplicated deterministically (SPEC.md §9).
- Schema migrations do not require migrating graph data — rebuild the projection instead (SPEC.md §4).

### Negative / Constraints

- Every read path that needs graph structure pays projection cost; the graph must be kept in sync via `projection.checkpointed` events (SPEC.md §9).
- UPDATE/DELETE are forbidden outside test builds — fixing a bad event means appending a correction, not editing (SPEC.md §11; AGENTS.md rule 1).

### Neutral

- Two storage engines must be maintained (SQLite + Kuzu), each with its own schema (SPEC.md §11).
