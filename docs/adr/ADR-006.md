# ADR-006 — Preserve Source Telemetry Extensions

- **Status:** Accepted (SPEC.md §7)
- **Source:** SPEC.md §7 (ADR-006), §9 (CanonicalEventEnvelope — extensions), §6 (OpenTelemetry adoption), §12 (Adapters); ARCHITECTURE.md §2, §5.4

## Context

CATG ingests heterogeneous sources — ADR AgentEvents, OTLP JSON spans, MCP client/server events — each carrying source-specific fields that the canonical model does not fully map (SPEC.md §1, §12). OpenTelemetry attributes in particular are numerous, vendor-specific, and "unstable attribute names" must not become dependencies of the domain model (SPEC.md §6 — "No dependence on unstable attribute names"). Yet dropping unmapped fields wholesale would destroy information that investigators, detectors, and cross-adapter comparisons may need (SPEC.md §24 risk "Cross-adapter inconsistency — invalid comparisons"). A versioned normalization layer is required (SPEC.md §6 — "Versioned normalization layer" under OTel GenAI conventions).

## Decision

**Canonical events retain a bounded `extensions` object carrying source telemetry extensions** (SPEC.md §7 ADR-006; SPEC.md §9 CanonicalEventEnvelope includes `extensions`).

- `CanonicalEventEnvelope` includes: eventId, schemaVersion, eventType, occurredAt, observedAt, producer, subject, trace context, identity context, payload, provenance, security classification, integrity hash chain, and `extensions` (SPEC.md §9).
- The extensions object is **bounded** — it preserves source-specific fields without letting them become part of the canonical payload contract (SPEC.md §7 ADR-006).
- Adapters map known fields into the canonical payload and preserve the remainder in extensions; the domain model never depends on unstable attribute names (SPEC.md §6, §12).
- Extensions are covered by the event's integrity hash chain like any other field (SPEC.md §9).

## Consequences

### Positive

- Source fidelity: OTel/MCP/ADR-specific fields survive ingestion for investigation and future adapters (SPEC.md §6, §12).
- Canonical payloads stay stable and vendor-neutral; attribute-name churn is contained inside adapters (SPEC.md §3, §6).
- Cross-adapter comparison and golden fixtures can account for extension content explicitly (SPEC.md §21).

### Negative / Constraints

- Extensions must be bounded — unbounded preservation would reintroduce the schema drift the canonical model exists to prevent (SPEC.md §7 ADR-006).
- Extension content is source-defined and must be treated as untrusted data in detectors (SPEC.md §14; ADR-005).

### Neutral

- Schema evolution of the canonical model proceeds by versioned normalization; extension fields may graduate into canonical fields in a later schema version (SPEC.md §6 "Versioned normalization layer").
